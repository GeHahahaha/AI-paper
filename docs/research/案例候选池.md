# 基于 Pi + MCP AI 研发工作流的案例候选池

## 一、先说结论

当前确定的征文案例组合是：

1. **某存量金融业务系统的需求逆向与整系统重构**：已经完成整系统重写、全部研发环节、内部验收和上线运行，证明工作流能够深入处理复杂、跨阶段的真实研发任务。
2. **开源组件漏洞的全机构排查与试点整改**：已经在全机构数十个项目中完成影响排查，并对选定试点项目完成整改，兼具金融安全属性和跨项目推广价值。

**提交触发的 AI 连续代码质量审核不作为独立案例。** 它是工作流的公共质量节点，在遗留系统重新实现、组件漏洞整改和日常研发中，每次代码提交都可触发相同的质量审核机制。

其他较有价值的方向依次是：

4. 从运行告警到修复 PR 的智能缺陷闭环。
5. 监管或制度变化驱动的跨系统影响分析与研发落地。
6. 存量系统单元测试资产自动构建。
7. 变更风险评估与发布证据包自动生成。

不建议把“代码生成”“研发知识问答”“自动写文档”等单点功能作为主案例，这些场景创新性和完整性较弱，也难以证明组织级价值。

> **2026 年 8 月 11 日项目组补充确认：**案例一原系统约 3 万行代码，已完成需求逆向、整系统重新设计与重写、测试、审核、验收和上线运行；案例二已真实执行全机构排查并完成试点项目整改，保留分支、提交、PR、测试和代码审核记录。正式申报稿统一使用匿名功能名称。

## 二、案例筛选标准

一个适合本次比赛的案例，最好同时满足：

- **场景真实**：解决正在发生的金融科技研发、质量、安全或稳定性问题。
- **流程完整**：至少覆盖需求或任务受理、分析、实施、测试、审核和交付中的多个阶段。
- **价值可量化**：能统计周期、人工投入、缺陷、覆盖率、成功率或风险拦截结果。
- **风险可控制**：AI 不直接绕过审批，不直接操作生产数据或未经授权发布生产。
- **方法可复制**：不是只适用于一个项目，可以通过知识、Skill、Rule、连接器和流程模板推广。
- **能体现 Pi + MCP 分工**：Pi 负责理解、规划和执行，MCP 负责受控连接外部平台。

## 三、案例一：某存量金融业务系统的需求逆向与整系统重构

### 1. 推荐案例名称

> 从源码到可维护系统：AI 驱动的需求逆向与整系统重构实践

### 2. 解决的问题

- 系统长期无人维护，原始设计人员、需求和架构知识缺失。
- 仅有源码及有限运行信息，业务规则和系统边界难以确认。
- 传统人工阅读源码投入大，容易遗漏隐含逻辑和异常分支。
- 原系统约 3 万行代码，直接修改风险较高，整系统重写又需要先建立可信的需求和验收基线。

### 3. 工作流

> 任务定义 → MCP 获取源码与历史信息 → AI 逆向候选需求 → 人工确认业务语义 → 架构与接口设计 → 任务拆分 → 隔离环境整系统重写 → 自动测试 → AI 代码审核 → 人工验收 → 上线运行 → 知识资产沉淀

### 4. 最值得强调的创新点

- 不把 AI 对源码的一次性总结当作需求，而是区分“代码事实、模型推断、人工待确认事项”。
- 将逆向需求继续送入设计、开发、测试和审核流程，形成完整证据链。
- 重新实现不是一次性代码生成，而是通过小步提交、测试反馈和独立审核持续收敛。
- 最终同时交付系统和需求、架构、测试、规则等可维护资产。
- 项目已经完成全部研发环节、内部验收和上线运行，可用真实过程记录验证完整闭环。

### 5. 建议指标

- 逆向恢复的需求、业务规则、接口和数据对象数量。
- 完成重新实现的模块及功能比例。
- 新增测试数量、覆盖率和关键业务链路通过情况。
- 人工代码阅读、需求梳理和开发周期变化。
- 发现的旧系统缺陷、矛盾规则或未覆盖异常情况。
- 上线后的正常运行周期、问题反馈及后续维护情况。

### 6. 主要风险

- 旧代码行为不一定等于正确业务需求。
- AI 可能把技术实现细节错误解释为业务规则。
- 重新实现可能遗漏低频但关键的边界逻辑。

控制方法是对需求进行来源标记、人工确认和行为对照，并使用测试、历史数据及运行行为交叉验证。

## 四、公共质量节点：提交触发的 AI 连续代码质量审核

### 1. 推荐案例名称

> 从人工抽查到提交必审：AI 驱动的持续代码质量门禁实践

“代码审核平台”应描述为贯穿各类研发任务的“持续代码质量门禁”，而不是单独包装成业务案例。

### 2. 解决的问题

- 人工代码审核深度受人员经验、时间和项目压力影响。
- 静态检查主要处理固定规则，难以理解跨文件语义、任务背景和变更影响。
- 开发人员主动使用 AI 审核容易被跳过，规则和结果也无法统一沉淀。
- 同类缺陷反复出现，人工审核结论难以变成组织级规则。

### 3. 工作流

> 代码提交 / 合并请求 → 自动触发审核 → MCP 获取差异、相关代码、任务背景和项目规则 → 审查 Agent 多维审核 → 问题分级与证据生成 → 结果回写代码平台 → 开发整改或说明 → 人工确认 → 规则与评价任务更新

### 4. 审核维度

- 逻辑正确性和边界情况。
- 空指针、资源释放、内存和线程安全。
- 异常处理、日志、错误码和可观测性。
- 输入校验、权限、敏感数据和安全风险。
- 跨文件调用关系与变更影响。
- 可维护性、重复逻辑和项目编码规则。
- 测试充分性及建议补充的测试场景。

### 5. 最值得强调的创新点

- 每次提交自动触发，不依赖开发人员主动调用。
- 审核差异时同时获取任务、代码、规则和历史上下文。
- 支持模型替换或多模型评价，平台能力不绑定单一厂商。
- 审核意见、整改和不采纳原因全部留痕，可持续评估有效率和误报率。
- 将已确认问题反向沉淀为 Rule、审核模式和评价任务。

### 6. 建议指标

- 接入项目、仓库和开发人员数量。
- 审核提交或合并请求数量。
- 问题总量及严重度分布。
- 有效问题率、整改率、采纳率和误报率。
- 高风险问题上线前拦截数量。
- 审核平均耗时与人工审核投入变化。
- 同类问题的重复出现率变化。

### 7. 可进一步升级的能力

- 严重问题阻断合并，一般问题进入人工确认。
- 自动建议或生成补充测试。
- 对整改后的新提交进行二次复核。
- 将审核结果纳入项目质量趋势和风险画像。

## 五、案例二：开源组件漏洞的全机构排查与试点整改

### 1. 推荐程度

这是当前选定的第二个主案例，原因是：

- 与金融 AI 安全、风险防控和系统稳定性直接相关。
- 能完整展示 Pi 的规划、并行 Agent 和失败修复能力。
- 能展示 MCP 同时连接安全平台、代码仓库、测试和发布系统。
- 结果客观，容易用漏洞数量、项目数量和整改周期衡量。
- 不需要让 AI 直接操作生产环境，风险相对可控。

### 2. 推荐案例名称

> 从漏洞通告到整改证据：AI 驱动的全机构排查与试点整改工作流

### 3. 典型场景

收到外部单位同步的开源组件漏洞通告后，传统方式需要人工：

- 查询哪些系统使用了该组件及受影响版本。
- 联系各项目负责人确认影响。
- 查找兼容版本和升级方法。
- 分项目修改、测试和审核。
- 汇总整改进展、残余风险和发布证据。

项目多时，这一过程容易耗时且信息分散。

### 4. 工作流

1. 安全平台、漏洞通告或人工任务触发工作流。
2. Pi 建立漏洞处置任务契约，明确严重度、时限和验收标准。
3. MCP 连接组件清单、代码仓库和依赖扫描系统，识别受影响项目。
4. 架构和开发 Agent 分析直接依赖、间接依赖、兼容性和潜在影响。
5. Pi 按项目风险和依赖关系生成整改计划，选定试点项目进入实施闭环。
6. 开发 Agent 在试点项目受控分支中升级组件、调整代码和配置。
7. 测试 Agent 运行构建、单元、集成及关键回归测试；失败自动归因和修复。
8. 审查 Agent 检查升级有效性、兼容风险和残余漏洞。
9. 生成试点整改 PR、全机构影响清单、测试证据、残余风险和后续处置建议。
10. 试点项目负责人审批合并和发布，平台持续跟踪全机构排查与其他项目处置状态。
11. 将漏洞模式、升级经验和兼容问题沉淀为知识、Rule 和评价任务。

### 5. 建议指标

- 从漏洞通告到完成影响范围识别的时间。
- 排查项目数、受影响项目数、完成试点整改项目数和受影响版本数量。
- 试点范围内自动生成或辅助完成的整改 PR 数量。
- 构建和测试一次通过率。
- 人工介入、整改失败和兼容问题分布。
- 从漏洞通告到整改完成的总体周期。
- 整改后残余漏洞及复发情况。

### 6. 风险控制

- AI 只创建候选修改和 PR，不直接发布生产。
- 组件版本和修复建议必须来自经过授权的安全信息源。
- 每个项目独立构建、测试、审核和审批。
- 无法确认兼容性的项目转人工分析，不强行自动升级。

## 六、扩展案例：从运行告警到修复 PR 的智能缺陷闭环

### 1. 推荐案例名称

> 从告警到修复建议：AI 驱动的生产问题研发闭环

不建议使用“生产自愈”作为名称，容易让评委认为 AI 会绕过人工直接修改生产系统。“从告警到修复 PR”更准确、更安全。

### 2. 工作流

> 告警或工单 → MCP 获取日志、指标、链路、近期变更和相关代码 → Pi 形成问题假设 → 在隔离环境复现 → 根因分析 → 生成修复和回归测试 → 独立审核 → 创建 PR → 人工确认 → 发布后持续观察

### 3. 价值

- 打通运维反馈与研发过程。
- 减少日志、代码、提交和工单之间的人工检索。
- 用可复现测试验证根因和修复结果。
- 将故障模式沉淀为告警处理 Skill 和回归测试。

### 4. 建议指标

- 告警到初步归因时间。
- 告警到修复 PR 时间。
- 根因判断准确率和一次修复成功率。
- 自动完成和人工接管的任务比例。
- 同类问题复发率。

### 5. 适用边界

- AI 只分析只读生产信息，修复在隔离研发环境完成。
- 生产操作、发布和回滚继续由授权人员执行。
- 涉及敏感业务数据的日志必须先脱敏和最小化。

## 七、扩展案例：监管或制度变化驱动的跨系统变更

### 1. 推荐案例名称

> 从制度要求到研发任务：AI 驱动的跨系统变更影响分析与交付实践

### 2. 为什么有金融特色

金融机构经常需要将监管要求、内部制度或安全规范落实到多个业务和技术系统。困难不只是理解文件，而是确定：

- 哪些系统、接口、数据项和流程受影响。
- 现有代码和规则与新要求存在哪些差距。
- 应修改哪些需求、设计、代码和测试。
- 如何证明变更已经完整落实。

### 3. 工作流

> 制度或规则输入 → 人工确认适用范围和正式解释 → MCP 检索项目、架构、数据和代码资产 → Pi 生成影响矩阵 → 专业人员确认 → 生成项目任务和验收条件 → 设计与开发 → 回归测试 → 代码审核 → 形成交付与合规证据

### 4. 创新点

- 将制度文本与项目、架构、代码、测试和发布证据连接起来。
- 不让 AI 单独作出监管解释，专业人员负责适用范围和业务语义。
- 形成“要求—系统—代码—测试—交付证据”的可追踪关系。

### 5. 建议指标

- 影响系统和需求识别时间。
- 人工确认后的影响项准确率和遗漏率。
- 自动生成任务、验收条件和测试建议数量。
- 从制度发布到完成研发整改的周期。

### 6. 实施难点

该案例金融特色最强，但需要业务、合规和技术人员共同参与，数据准备及事实确认成本较高，更适合作为中期试点，而不是在申报截止前临时包装。

## 八、扩展案例：存量系统单元测试资产构建

### 1. 推荐案例名称

> 从无测试到可回归：AI 驱动的存量系统测试资产建设

### 2. 工作流

> 代码与变更历史分析 → 风险模块识别 → 测试范围和用例设计 → 测试代码生成 → 编译运行 → 失败归因和修复 → 用例独立审核 → 覆盖率与风险报告 → 人工验收

### 3. 价值

- 将开发人员经验转化为可持续执行的测试资产。
- 为遗留系统维护、组件升级和代码重构建立安全网。
- 能与代码审核平台结合：审核发现测试不足后自动发起测试补充任务。

### 4. 建议指标

- 新增测试数量和覆盖率变化。
- 关键风险模块覆盖情况。
- AI 生成测试的一次运行通过率和人工修改比例。
- 新增测试提前发现的缺陷数量。
- 回归测试时间变化。

## 九、扩展案例：变更风险评估与发布证据包生成

### 1. 推荐案例名称

> 从代码变更到发布证据：AI 驱动的变更风险评估与交付准备

### 2. 工作流

> 读取需求和提交差异 → 获取依赖、测试、审核和历史故障 → 识别影响模块与风险 → 检查测试充分性 → 生成变更说明、风险清单、发布步骤和回滚方案 → 人工审批

### 3. 价值

- 减少发布材料的人工汇总和信息遗漏。
- 建立需求、代码、测试、审核和发布之间的证据关系。
- 支持按变更风险确定审批和测试强度。

### 4. 局限

该场景实用且容易落地，但如果单独作为主案例，创新性可能不如遗留系统重建、代码质量门禁和漏洞应急整改，适合作为全流程工作流的一个组成环节。

## 十、组合建议

### 方案一：当前最稳妥的征文组合

1. 主案例：长期无人维护系统需求逆向与重新实现。
2. 主案例：开源组件漏洞跨项目应急整改。
3. 公共质量节点：提交触发的 AI 连续代码质量审核。
4. 辅助说明：Pi 单元测试资产构建。

优势是一个案例体现复杂系统重建，一个案例体现跨项目安全整改，代码审核平台则证明两类任务共用同一质量底座。

### 方案二：安全与风险特色最强

1. 主案例：开源组件漏洞跨项目应急整改。
2. 扩展案例：监管或制度变化驱动的跨系统影响分析。
3. 公共质量节点：提交触发的 AI 连续代码质量审核。
4. 辅助环节：发布风险评估与证据包。

优势是与金融 AI 安全、风险防控和合规性高度匹配。

### 方案三：全生命周期展示最完整

1. 主案例：长期无人维护系统需求逆向与重新实现。
2. 主案例：从运行告警到修复 PR 的缺陷闭环。
3. 平台底座：提交触发的 AI 连续代码质量审核。

优势是覆盖需求、设计、开发、测试、审核、交付和运行反馈，但对系统接入和数据准备要求最高。

## 十一、结合申报时间的建议

线上申报截止日为 **2026 年 8 月 28 日**。在剩余准备时间有限的情况下：

- 正文案例调整为“遗留系统重建 + 组件漏洞跨项目应急整改”，代码审核平台作为两个案例共用的质量节点。
- 两个案例均已真实执行，不再安排为了征文而进行的临时演练；当前应从既有记录中补齐准确统计口径和脱敏证据。
- 组件漏洞案例严格写成“全机构排查 + 试点整改完成”，不得扩大为所有受影响项目均已完成整改。
- 不建议为征文临时接入生产操作或开展高风险自动发布。
- 监管变化和告警修复闭环可写入推广规划，但没有真实任务数据时不要包装为已落地案例。
