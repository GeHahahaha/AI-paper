# Harness 工程实践材料评估与吸收建议

## 一、结论

《../../materials/internal/Harness工程在机构投票应用中的探索实践.md》对征文有明显提优作用，不建议弃用。

它提供了当前大纲最缺少的三类内容：

1. **真实项目载体**：机构投票应用，而不是抽象或模拟任务。
2. **可复述的工程方法**：四阶段质量门禁、TDD、独立审查、失败回退和证据链。
3. **初步量化事实**：三周周期、五人天人工投入、单元测试覆盖率达到 80% 门禁，以及 Agent、技能和流程命令等资产沉淀。

但 Harness 不应与 Pi + MCP 并列成两套方案。推荐关系是：

> Harness 是在机构投票项目中验证 AI 全流程研发方法的案例级实践；Pi + MCP 是总体的通用化、平台化架构。将 Harness 验证出的质量门禁、独立审查和上下文治理机制吸收到 Pi + MCP 工作流中。

这样既保留真实案例，又不会破坏当前征文“Pi 负责执行、MCP 负责连接、人工负责关键决策”的主线。

> **2026 年 8 月 11 日项目组补充确认：**案例实际范围为整套系统重新设计与重写，原系统代码约 3 万行；需求逆向、设计、开发、单元测试、集成测试、代码审核和交付门禁均已完成；系统已经完成内部验收、正式上线并正常运行。正式申报稿统一采用匿名案例名称，不公开机构投票、Harness、模型、工具和平台真实名称。

## 二、建议吸收的内容

### 1. 四阶段质量门禁

Harness 将项目实践划分为：

1. 需求与设计。
2. TDD 开发。
3. 集成验证。
4. 交付提交。

每个阶段都有明确交付物、独立审查和回退条件。这可以作为 Pi 自主任务执行子流程在机构投票项目中的具体落地形态。

### 2. 开发与审查分离

- 开发 Agent 和审查 Agent 使用独立上下文。
- 需求、单元测试和集成测试方案分别设置专门审查 Agent。
- P0/P1 问题阻断流程，整改后重新审查。

该机制比笼统描述“AI 参与代码审核”更具体，也能支撑“质量控制前置、同一模型不同时充当运动员和裁判”的创新点。

### 3. TDD 硬门禁

- RED：根据需求规格编写测试。
- RED 审查：检查覆盖范围、边界条件和反模式。
- GREEN：实现功能并迭代至测试通过。
- 单元测试覆盖率门禁为 80%。

80% 应写成机构投票项目的案例阈值，不应直接写成所有项目统一标准。

### 4. 集成验证闭环

- 编写端到端集成测试方案。
- 独立审查业务场景、规则和边界覆盖。
- 使用浏览器自动化执行冒烟测试。
- 出现问题后执行“补测试—修代码—重跑全量”的循环。

这能补强当前大纲中测试验证阶段过于概括的问题。

### 5. 需求逆向方法

- 从代码中提取业务规则、校验逻辑和交互流程。
- 形成需求规格初稿。
- 由独立需求审查 Agent 逐条审核。
- 人工确认和补充业务语义。

征文中应进一步区分“代码事实、AI 推断和人工确认”，避免把旧代码行为直接等同于正确需求。

### 6. 大型代码库上下文治理

Harness 材料提出使用代码知识图谱处理大型项目上下文溢出问题。该方法可以吸收到 MCP 上下文构建机制中：

- 将代码结构转换为可检索的模块、调用和依赖关系。
- Agent 按任务查询相关模块，而不是一次加载整个代码库。
- 上下文获取过程保留来源、范围和版本信息。

征文正文可以写“代码图谱或结构化代码索引”，具体产品名称 Graphify 可放在案例细节中，不必作为总体方案依赖。

### 7. 真实资源与成效数据

材料提供了以下可用事实：

- 实践周期为三周。
- 人工投入约五人天，主要用于需求确认和关键节点决策。
- 单元测试覆盖率达到 80% 案例门禁。
- 形成审查 Agent、开发技能和流程命令等可复用资产。

这些数据应补充统计口径后写入案例，尤其要说明：

- 三周的起止范围和交付范围。
- 五人天是否包含需求确认、环境准备、审查和验收。
- 80% 覆盖率的计算工具、代码范围和排除项。
- 资产数量存在“审查 Agent 三类”和“资产沉淀四类审查 Agent”的表述差异，需要确认。

### 8. 诚实描述局限

材料明确写出了：

- Agent 通用性仍需通过其他项目验证。
- 部分需求确认、报告评审和浏览器登录仍依赖人工。
- 尚未实现全流程无人值守。

这些内容不应删除。适度说明局限能够强化案例真实性，也与当前方案“自主可控不等于无人参与”的定位一致。

## 三、不建议直接吸收的内容

### 1. Qoder 与外网执行作为主要方案

材料中“将内网生成的需求拿到外网环境中使用外部算力开发”的表述，与当前征文强调的数据边界、受控环境和自主可控存在明显冲突。

建议处理：

- 不在正文中描述具体的内外网搬运过程。
- 如需说明，可写成“先行探索暴露了算力供给与数据安全之间的矛盾”，由此引出后续模型路由、分类分级和受控连接设计。
- 正式方案统一使用 Pi + MCP、受控算力环境和数据分类分级表述。

### 2. 超大 Token 消耗

“约 5.1 亿 Token”和“约 9,000 credits”缺少统一价格、任务范围和对照基线，直接写入可能强化成本过高的印象。

建议暂不用于征文核心成效。只有在能够补充以下信息后再考虑使用：

- 调用周期和任务范围。
- 缓存、重复调用及失败重试占比。
- 与人工成本或其他模型方案的对照。
- 后续通过代码图谱、上下文压缩和模型路由实现的成本下降。

### 3. “全流程无人值守”

该表述与材料中人工参与较多的事实矛盾，也容易引发金融安全和责任问题。

建议统一改为：

> 低风险、可验证任务由 AI 自主执行，需求语义、质量验收、代码合并和生产发布等关键节点由人员决策。

### 4. 将 Harness 描述为另一套独立平台

如果正文同时存在 Harness、Pi、MCP、Qoder、Graphify 和代码审核平台，评委容易无法判断系统边界和核心创新。

建议统一层级：

- Harness：机构投票项目中的工程实践方法和流程模板。
- Pi：通用化后的自主执行中枢。
- MCP：通用化后的外部系统连接与治理层。
- 代码审核平台：公共质量门禁。
- 代码图谱：上下文构建的一项支撑能力。

## 四、需要确认的冲突与缺口

### 1. “重新实现”的实际范围

Harness 原始材料只描述了需求分析、功能开发和集成测试，材料本身未证明整个系统已经全部重写；项目组已于 2026 年 8 月 11 日补充确认实际范围和最终状态。

已经确认：

- 在约 3 万行原系统源码基础上完成整套系统重新设计与重写。
- 需求、设计、开发、测试、代码审核和交付门禁全部完成。
- 系统通过内部验收、正式上线并正常运行。

正式稿采用匿名后的表述：

> 基于源码逆向恢复需求，完成某存量金融业务系统的整系统重新设计、重写、验证和上线交付。

### 2. 审查 Agent 数量

正文列出三类审查 Agent：

- 需求审查。
- 单元测试审查。
- 集成测试方案审查。

资产沉淀部分又写“四类审查 Agent”。需要确认第四类是否为代码审查 Agent 或交付审查 Agent。

### 3. 模型与工具版本

模型、Qoder、Graphify 等具体名称可以保留在内部过程记录中。正式征文中应以能力和机制为主，只在确有必要时写产品名称，并确认版本、部署方式及可公开性。

### 4. 需求逆向与人工确认记录

需要补充：

- 逆向形成了多少条需求、规则、流程或接口。
- 其中多少可由代码直接证明，多少需要人工确认。
- 审查发现了多少缺失、歧义或代码与原文档不一致的问题。

### 5. 质量和交付结果

需要补充：

- 单元测试数量和覆盖范围。
- 集成测试场景和执行结果。
- 发现并修复的问题数量及严重度。
- 上线后的稳定运行周期和后续维护反馈。

## 五、对征文主线的提优方式

建议将总体叙事调整为：

1. 机构首先在长期演进、文档不完整的机构投票项目中开展 Harness 工程实践。
2. 实践验证了质量门禁、独立审查、TDD、代码图谱和证据链的有效性，也暴露了工具分散、算力、安全和通用性问题。
3. 将 Harness 实践经验与既有 Pi、MCP 能力整合，形成自主可控 AI 研发工作流的通用方案。
4. 再以开源组件漏洞跨项目应急整改验证该通用工作流能否跨项目复制。
5. 提交触发的 AI 代码审核平台作为两个案例共用的质量节点，证明质量能力已平台化。

这一叙事比单纯介绍一套目标架构更可信，因为它形成了：

> 真实项目探索 → 方法沉淀 → 平台抽象 → 跨项目复制
