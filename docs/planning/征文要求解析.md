# “人工智能+”金融科技创新应用大赛征文要求解析

## 结论：按“创新案例”准备，不按普通征文准备

活动正式名称为“2026 年上海金融系统职工‘人工智能+’金融科技创新应用大赛”，主题为“AI 领航，建功新程”。与通常所说的征文不同，本次需要申报的是 **创新案例赛道项目**：核心不是阐述观点、罗列技术趋势或写一篇理论文章，而是用真实案例说明 AI 如何解决金融场景中的实际问题，并证明该方案安全、有效、可推广。

因此，本文后续所说的“征文”，均应理解为 **案例申报正文及其配套路演材料**。

## 1. 申报方向：本项目应落在哪一类

活动列出的方向包括：

1. 大模型驱动的金融应用范式创新，含多智能体协同与轻量化部署。
2. 金融 AI 安全加固、伦理对齐与风险防控。
3. 面向“五篇大文章”的智能金融服务生态。
4. 智能化资产管理科技。
5. 保险科技创新与价值链重塑。
6. 数字人民币场景深化与创新应用。
7. 其他利用新技术、新手段推动金融业务创新与效率提升的实践。

**推荐定位：第 7 类为主，第 1 类为辅。**

项目核心价值是建设以 Pi 为自主执行中枢、以 MCP 为受控连接层的金融科技 AI 研发全流程，最稳妥的归类是“推动金融业务系统研发与运维效率提升的实践”。如果申报表允许填写标签或关键词，可补充“多智能体协同”“可信 AI 研发”“全流程自主交付”“MCP 受控连接”。

不要把重点放在“使用了 Pi、MCP 或多个大模型”上。评审看的是金融场景中的问题、解决办法和价值，工具与协议只是技术实现的一部分。

## 2. 案例必须回答的四个问题

活动辅导材料明确要求，优秀案例要讲清以下四项；建议它们直接成为申报正文的一级标题。

### 2.1 应用背景：解决什么金融业务痛点

要从“AI 已进入多个研发环节，但仍是分散工具，尚未形成可治理的交付闭环”的真实困境切入，并把研发问题翻译成金融科技问题：

- 项目、代码、测试、发布和运维信息分散，AI 缺少连续、可信的任务上下文。
- 单点生成结果缺少统一验证、独立审查和失败修复机制，难以直接形成交付能力。
- Agent 接入代码、终端和外部平台后，权限、执行、安全和责任风险明显扩大。

不要只写“AI 技术发展迅速”或“团队希望提升效率”；必须说明不解决会带来的具体风险和成本。

### 2.2 技术方案：AI 如何真正落地

应写成可复现的工程流程，而不是产品介绍。建议表达为：

> 任务受理与风险分级 → MCP 构建上下文 → Pi 需求与方案设计 → Agent 规划与实施 → 自动验证与失败修复 → 独立审查 → 人工审批与受控交付 → 运行反馈与能力沉淀

每个环节至少交代六件事：输入是什么、Pi 做什么、MCP 调用什么、怎样校验、谁负责最终决定、沉淀什么证据。尤其要写清 Pi 是流程执行中枢，MCP 是受控连接层，不替代既有权限、审批和责任体系。

### 2.3 实施效果：产生哪些实际价值

这是材料最容易薄弱、但最影响竞争力的部分。效果必须尽量有“前后对比 + 样本范围 + 统计周期”。

建议从以下方面选择真实指标：

- 项目认知：已梳理模块数、核心链路数、沉淀规则/说明数、典型问题定位耗时。
- 测试质量：新增测试数、覆盖率变化、关键模块覆盖情况、回归耗时、提前发现的缺陷。
- 代码质量：触发审查的提交数、有效问题数或采纳率、问题分类、上线前拦截案例。
- 组织效率：维护任务周期、人工审查投入、新成员上手时间、可复用工作流覆盖的项目数。

没有可公开的绝对数时，可使用比例和区间，但必须注明口径。没有稳定数据时，用一个可匿名化的完整案例说明“问题—AI 发现/生成—人工验证—最终结果”，比空泛的“提效明显”更有说服力。

### 2.4 风险控制：如何保证安全、合规、可控

这是金融场景的硬要求，不能用一句“遵守数据安全规范”带过。建议至少写清：

- **数据边界**：源码、文档、测试数据在授权和脱敏范围内接入；敏感内容按分级要求处理。
- **权限边界**：按最小权限配置工具；AI 不直接修改生产数据、不直接执行生产操作。
- **质量边界**：AI 输出必须经编译、测试、代码审查和人工验收；不能直接视作事实或直接合并。
- **审计边界**：任务输入、审查结论、测试结果和人工处置过程留痕，便于复盘和追溯。

## 3. 评审真正看什么

活动决赛采用现场路演和专家综合评价，明确关注三项：

1. **合规性**：是否符合金融监管、数据安全和相关合规要求。
2. **适用性**：是否解决了实际业务问题，是否具备落地应用价值。
3. **创新性**：技术融合、业务模式或应用场景是否有创新特点。

对此项目而言，建议优先级是：

> **适用性（真实研发交付问题） → 合规性（人机边界、MCP 受控接入与全过程审计） → 创新性（Pi 驱动的全流程自主协同与双闭环运营）。**

不能只强调模型能力或多 Agent 概念。对评审而言，“有受控边界的真实成效”比“看起来更自动化”更重要。

## 4. 时间、流程与交付准备

- **线上申报截止日：2026 年 8 月 28 日。**
- 申报后依次经历：在线审核、初审/复赛、决赛评比、成果展示。
- 初审和复赛阶段预计在 **2026 年 8 月 28 日至 9 月中旬**；可能有合议审查、现场答辩和专家评审。
- 决赛预计在 **2026 年 10 月中下旬**，形式为现场路演与专家打分。
- 每家机构原则上最多申报 3 个项目。

活动材料未明确给出案例正文的字数、固定文档模板或附件格式。因此，当前应先形成一份结构完整、事实严谨的案例正文，并尽早在申报平台核对字段限制、是否需要 PDF/Word/PPT、是否支持图片或视频材料。

## 5. 建议的申报材料包

在平台格式未确认前，建议按下面的材料包准备，后续可按需裁剪：

1. **案例正文**：约 3,000—5,000 字，严格对应“背景—方案—效果—风控—创新—推广价值”。
2. **一页总体流程图**：展示“认知—验证—审查—反馈”的闭环及人工责任节点。
3. **数据附件**：指标口径说明、脱敏统计截图或图表、1—2 个代表性案例。
4. **风险控制说明**：数据、权限、操作、审计和人工验收边界。
5. **路演稿基础材料**：6 页左右的提炼版 PPT，避免后期临时重写。

## 6. 本项目的“得分写法”

### 应重点强调

- 这是一个面向 **真实金融科技研发任务** 的执行体系，而非通用演示。
- Pi 将需求、设计、开发、测试、审查、交付和运行反馈组织为连续任务状态。
- MCP 统一连接外部研发系统，并实施最小权限、参数校验、凭据托管和调用审计。
- 全流程自主协同的前提是人机分工明确、关键操作由人负责、全过程可追溯。
- 成果可以通过知识、Skill、Rule、流程模板、连接器和评价任务复制到更多项目。

### 应避免的表述

- “AI 自动完成全流程研发”“无人值守修改核心系统”等容易引发合规担忧的说法。
- 未经确认的提升比例、缺陷数量、成本节约金额。
- 只写模型名称、工具数量或调用次数，不写解决的问题和验证结果。
- 将内部技术术语直接堆入材料，未解释业务价值和人工控制方式。

## 7. 当前准备缺口与优先动作

现有内部报告已经足以建立文章骨架，但要形成高质量申报，还差“案例事实”和“效果证据”。建议优先完成：

1. 选定一组覆盖需求到交付的代表性真实研发任务，确认可公开范围及当前已落地阶段。
2. 汇总测试、代码审查和维护任务的真实数据，统一统计口径。
3. 明确模型部署、代码/数据接入、权限控制、日志审计和人工审批的实际做法。
4. 由项目负责人确认哪些效果可用作正式申报事实，哪些只能作为内部素材。
