### 2. 申报方向

### 3. 核心主张

文章不以某个模型、工具或单一功能为中心，而是介绍一套由本所自主设计和掌控的 AI 研发工作流：

- Pi 负责研发任务的理解、规划、Agent 编排、执行、验证、审查和复盘。
- MCP 负责受控连接项目、知识、代码、测试、质量、发布和运维系统。
- 人工负责目标、验收标准、高风险方案、代码合并、生产发布和异常处置。
- 通过真实任务验证和能力运营闭环，把个人使用 AI 的经验沉淀为可复用、可审计、可持续优化的组织能力。

本文中的 Harness 工程是机构投票项目中的案例级工程方法；Pi + MCP 是总体的通用化、平台化架构。Harness 验证出的质量门禁、独立审查和上下文治理机制被吸收到 Pi + MCP 工作流中，两者不是并列的两套架构。

### 4. 案例组合

正文建议重点写两个完整案例：

1. **深度案例：长期演进、维护知识缺失的存量系统需求逆向与重新实现。** 证明工作流能够承接上下文缺失、跨阶段、复杂度较高的完整研发任务；在实施范围确认前，正文统一表述为“完成目标业务范围的重新设计与实现”。
2. **安全案例：开源组件漏洞的跨项目应急分析与批量整改。** 证明工作流能够跨项目完成影响识别、整改、测试、审核和证据化交付。

提交触发的 AI 代码审核平台不是独立案例，而是工作流中贯穿开发、漏洞整改和交付验收的公共质量节点。单元测试资产构建、缺陷修复闭环等场景可以作为辅助说明或后续推广方向。

## 二、摘要写作要点

摘要建议按照“问题—方案—案例—价值—边界”组织，不在摘要中罗列行业趋势。

1. **问题**：当前 AI 在研发中的应用多以代码补全、问答、测试生成等分散工具为主，缺少连续任务状态、跨平台协同、统一验证和安全治理。
2. **方案**：构建以 Pi 为自主执行中枢、以 MCP 为受控连接层、以人工检查点和安全治理为边界的 AI 研发工作流。
3. **案例**：将工作流用于长期演进、维护知识缺失的存量系统需求逆向和目标业务范围重新实现，以及开源组件漏洞的跨项目应急整改；提交触发的 AI 代码审核作为两个案例共用的质量节点。
4. **价值**：提升复杂系统认知、研发交付、测试验证和代码质量控制能力，使 AI 从单点辅助工具转变为组织级研发能力。
5. **边界**：核心代码合并、生产发布、生产数据和权限变更仍由授权人员决策，AI 全过程留痕并接受真实任务评价。

> 人工智能；AI 研发工作流；智能体；MCP；代码审核；研发效能；自主可控

## 三、正文大纲

### 第一部分　应用背景：从分散辅助走向受控交付（约 10%—15%）

#### 1. 金融科技研发面临的现实问题

- 研发过程涉及需求、设计、代码、测试、质量、发布和运维等多个平台，信息容易割裂。
- AI 已进入多个研发环节，但大多是开发人员主动发起的一次性问答或生成任务。
- AI 生成的代码、测试和分析结果缺少连续上下文、统一验收标准、独立审查和完整证据。
- Agent 接入代码、终端和外部系统后，数据泄露、权限误用、工具滥用和错误执行风险进一步扩大。

#### 2. 单点工具无法解决的问题

- 代码生成速度提升不等于研发任务整体交付效率提升。
- 不同人员分别使用 AI，形成的提示词、规则和经验难以复用。
- 缺少从需求到运行反馈的完整闭环，失败无法系统复盘，能力也难以持续改进。
- 自动化程度越高，越需要清晰的人机责任和安全控制。

#### 3. 项目建设目标

建设一套不整体替换既有研发平台的 AI 研发工作流，使 AI 能够：

- 在任务级上下文中连续工作，而非停留在单次对话。
- 连接既有工具和数据，但不绕过现有权限与审批体系。
- 自主完成低风险、可验证任务，在关键风险节点交由人员决策。
- 形成测试、审查、决策和运行证据，使结果可验证、过程可追溯。

本部分结尾提出核心问题：

> 如何在保持金融研发责任体系和安全边界不变的前提下，让 AI 从代码辅助工具转变为能够承接完整研发任务的受控执行体系？

### 第二部分　技术方案：Pi 中枢、MCP 连接、人机协同（约 25%—30%）

#### 1. 总体架构

插入 **图 5《AI 增强研发全生命周期总图》**。

以传统研发生命周期为主轴：

> 任务受理 → 需求分析 → 方案设计 → 开发实施 → 测试验证 → 审查验收 → 发布交付 → 运行反馈

说明四个纵向层次：

1. 人工责任与检查点。
2. Pi 自主执行。
3. MCP 受控连接。
4. 数据、权限、执行、质量、审计和评价治理。

#### 2. Pi 自主任务执行机制

插入 **图 6《Pi 自主任务执行子流程》**。

按八个步骤介绍：

1. 建立任务契约：目标、范围、验收标准、风险等级和审批策略。
2. 构建任务上下文：通过 MCP 获取需求、代码、历史、测试和运行信息。
3. 规划与 Agent 编排：拆分步骤，选择专业 Agent、模型、工具和质量阈值。
4. 隔离环境执行：在受控分支与沙箱中实施代码、配置和文档变更。
5. 自动验证与修复：执行测试、静态和安全检查，失败后自动归因、修复和复测。
6. 独立审查与整改：以独立上下文检查正确性、安全性、合规性和变更影响。
7. 证据化交付：汇总 PR、变更说明、测试、审查、风险与回滚材料。
8. 反馈与能力沉淀：将运行反馈和失败案例沉淀为知识、Skill、Rule、流程模板及评价任务。

机构投票项目中的 Harness 实践将上述流程具体化为四阶段质量门禁：

1. 需求与设计门禁。
2. TDD 开发门禁。
3. 集成验证门禁。
4. 交付提交门禁。

每个阶段都有交付物、独立审查和失败回退条件，审查不通过不能进入下一阶段。

#### 3. Pi 智能体编排机制

插入 **图 7《Pi 智能体编排架构》**。

重点说明：

- 主控 Agent 维护任务状态、依赖、检查点、异常恢复和结果汇总。
- 需求、架构、开发、测试、审查、交付及运维 Agent 按角色分工。
- 所有 Agent 共享经过权限控制的任务上下文、计划、产物和证据。
- 策略与模型路由层根据任务风险、模型能力、数据敏感等级、稳定性和成本选择模型。
- 审查 Agent 使用独立上下文，避免开发与审查逻辑完全同源。
- 机构投票实践分别设置需求审查、单元测试审查和集成测试方案审查 Agent，并采用 A/B/C/D 质量评级和 P0/P1/P2 问题分级；具体数量和评级口径需在正文成稿前确认。

#### 4. MCP 外部交互机制

插入 **图 8《MCP 外部交互与治理子图》**。

MCP 调用链包括：

1. 工具发现与选择。
2. 身份映射与最小权限授权。
3. 上下文和参数校验。
4. 连接器受控执行。
5. 结果标准化与完整性校验。
6. 调用审计及任务状态回写。

明确 MCP 的定位：

- MCP 负责连接和控制，不负责研发方案决策。
- 外部系统凭据由连接层或既有凭据系统托管，不进入 Agent 长期上下文。
- 高风险写操作进入人工授权检查点。

#### 5. 贯穿开发与交付的 AI 代码质量审核节点

代码审核平台作为工作流的标准质量门禁，不单独包装成案例。

运行方式：

1. Pi 或开发人员完成代码提交、整改提交或合并请求。
2. 代码仓库事件自动触发 AI 代码审核平台。
3. 平台通过 MCP 获取代码差异、相关文件、任务背景、项目规则和历史问题。
4. 审查 Agent 从正确性、安全性、并发与内存安全、空指针、边界情况、异常处理、可维护性、测试充分性和变更影响等维度审核。
5. 平台将问题分级，给出位置、依据、影响和修改建议，并回写提交或合并请求。
6. 严重问题返回开发或漏洞整改环节，一般问题由人员确认处置。
7. 处置结果反哺审核 Rule、问题模式、评价任务和模型选择。

该节点在两个案例中承担相同职责：

- 在机构投票项目的目标业务范围重新实现中，审核新实现是否偏离确认后的需求和设计。
- 在组件漏洞整改中，审核漏洞是否真正消除、升级是否引入兼容性和安全问题。
- 在日常研发中，每次代码提交均可触发相同的质量审核机制，体现平台化和规模化基础。

#### 6. 两个闭环

- **研发交付闭环**：任务 → 需求 → 设计 → 开发 → 测试 → 审查 → 交付 → 运行反馈。
- **能力运营闭环**：运行记录 → 成效评价 → 失败复盘 → 能力更新 → 再验证 → 推广、降级或退出。

### 第三部分　实践案例一：Harness 工程在机构投票应用中的需求逆向与重建（约 15%—20%）

该案例用于证明工作流具有跨阶段处理复杂研发任务的能力。

#### 1. 案例背景

- 机构投票应用长期演进，原始人员和设计知识不足，需求理解和质量保障较依赖个人经验。
- 保留了源码及有限项目资料，但原始需求存在缺漏、不准确或与代码实际行为不一致的情况。
- 传统方式需要研发人员逐文件阅读代码、人工推断业务逻辑，修改影响范围和回归风险难以判断。
- 项目目标不是简单让 AI 生成代码，而是恢复可确认的需求和系统认知，并在质量门禁约束下完成目标业务范围的重新设计与实现。

#### 2. 工作流实施过程

建议按以下顺序写成一个完整故事：

1. **任务受理**：明确需要恢复的业务能力、系统边界、验收范围和不可触碰的安全边界。
2. **代码图谱与上下文构建**：将大型代码库结构化为模块、调用和依赖关系，Agent 按需查询相关代码，避免一次加载全部源码造成上下文溢出。
3. **需求逆向**：通过需求逆向提取命令，从代码中提取业务规则、校验逻辑和交互流程，形成需求规格初稿。
4. **需求独立审查**：需求审查 Agent 从完整性、可测性、安全性等维度审核；将“代码事实”“模型推断”和“待业务确认事项”分开，由人员确认关键语义。
5. **TDD RED 阶段**：基于确认后的需求规格先编写单元测试，并由独立 RED 审查 Agent 检查覆盖范围、边界条件和反模式。
6. **TDD GREEN 阶段**：开发 Agent 编写实现代码并迭代至测试通过，案例设置单元测试覆盖率不低于 80% 的质量门禁。
7. **集成验证**：设计跨模块集成测试方案，由独立审查 Agent 检查场景和业务规则覆盖，并通过浏览器自动化执行冒烟测试。
8. **失败修复循环**：发现问题后执行“补测试—修代码—重跑全量”，存在 P0/P1 问题则回退整改并重新审查。
9. **独立代码审核**：提交触发的代码审核平台检查实现正确性、安全性、异常处理、边界条件及项目规则。
10. **交付门禁与资产沉淀**：单元测试、集成测试和覆盖率全部达标后提交交付，并归档需求、审查、测试、代码和决策证据。

#### 3. 案例创新点

- 不是让 AI 对源码做一次性总结，而是通过完整工作流将源码认知转化为需求、设计、代码、测试和审查证据。
- 对逆向得到的需求区分“事实、推断和待确认项”，控制大模型对业务语义的误判。
- 采用“AI 执行 + 流程约束 + 独立审查”的 Harness 方法，质量检查被前置并强制嵌入各阶段。
- 开发 Agent 与审查 Agent 使用独立上下文，避免同一执行逻辑同时充当运动员和裁判。
- 重新设计与实现过程由 TDD、80% 案例覆盖率门禁、集成验证和提交触发的代码审核共同约束。
- 代码图谱使大型代码库能够按需检索，为后续 MCP 上下文连接机制提供了实践基础。
- 本轮实践形成可维护的需求、架构和测试资产，降低知识再次流失的风险。

#### 4. 需要补齐的数据

- 系统规模：代码量、模块数、接口数、核心业务链路数。
- 逆向成果：恢复的需求、规则、流程、接口或数据对象数量。
- 重新设计与实现范围：整个系统、目标模块还是新增功能，完成比例及验收边界。
- 测试效果：单元测试数量、80% 覆盖率的计算范围、集成场景和发现问题数量。
- 现有投入数据：项目历时三周，人工投入约五人天；需要补充统计起止、人员角色和工作内容。
- 质量结果：验收通过情况、上线或试运行稳定性、后续维护反馈。
- 资产沉淀：审查 Agent、开发技能和流程命令的准确数量；当前材料存在三类与四类审查 Agent 的口径差异。
- 成本数据：模型 Token 与 credits 暂不直接用于成效结论，除非能够补充统一成本和对照口径。

### 第四部分　实践案例二：开源组件漏洞跨项目应急整改（约 15%—20%）

该案例用于证明工作流能够在安全事件或漏洞通告触发后，跨多个项目完成影响识别、整改实施、测试审核、人工审批和证据化闭环。

#### 1. 案例背景

- 金融科技系统大量使用开源组件，一个高风险漏洞可能同时影响多个项目和版本。
- 传统处置需要人工查询依赖清单、联系项目负责人、分析兼容性并逐个项目整改。
- 项目数量较多时，影响范围识别、整改进度和残余风险容易分散，难以形成统一证据。
- 简单批量升级可能造成构建失败、接口不兼容或业务回归，不能只根据组件版本自动修改。

#### 2. 工作流实施过程

1. **任务触发**：安全平台、漏洞通告或人员发起应急整改任务，明确漏洞严重度、处置时限和验收标准。
2. **影响范围识别**：MCP 连接组件清单、依赖扫描和代码仓库，Pi 识别直接依赖、间接依赖、受影响项目及版本。
3. **兼容性分析**：架构和开发 Agent 分析可用修复版本、接口变化、项目约束和潜在影响。
4. **项目级整改计划**：Pi 按项目风险、依赖关系和负责人生成整改任务，配置测试范围和人工检查点。
5. **隔离环境整改**：开发 Agent 在各项目受控分支中升级组件并调整相关代码、配置和构建文件。
6. **自动测试与失败修复**：运行构建、单元、集成和关键回归测试；失败后自动归因、调整方案并复测。
7. **提交触发 AI 代码审核**：每次整改提交自动进入代码质量审核节点，检查漏洞是否消除、升级是否完整、兼容性和安全风险是否可接受。
8. **证据化交付**：生成项目清单、影响分析、整改 PR、测试报告、审核结果、残余风险和发布建议。
9. **人工审批与发布**：项目负责人审批合并和发布，高风险或无法确认兼容性的项目转人工专项处理。
10. **持续跟踪与沉淀**：MCP 回写整改状态，工作流持续跟踪未完成项目，并将漏洞模式、兼容问题和升级经验沉淀为知识、Rule 和评价任务。

#### 3. 案例创新点

- 将漏洞通告、组件清单、代码仓库、测试、代码审核和发布证据串成一条完整工作流。
- Pi 可以按项目拆分并行任务，但每个项目独立测试、审核和审批，兼顾效率与风险隔离。
- 代码审核平台不再只是日常辅助工具，而是漏洞整改流程中的标准质量检查点。
- 最终输出不仅是代码修改，还包括受影响范围、整改状态、验证证据和残余风险。
- 模型、扫描工具和代码平台通过 MCP 解耦，可按环境和安全等级替换。

#### 4. 需要补齐的数据

- 漏洞类型、严重等级、处置时限及选取该案例的原因。
- 扫描项目数、受影响项目数、直接和间接依赖数量。
- 从任务触发到完成影响范围识别的时间。
- 自动生成或辅助完成的整改分支、提交和 PR 数量。
- 构建、测试和代码审核的一次通过率及失败原因分布。
- 人工介入项目数、兼容性问题数和残余风险。
- 从漏洞通告到整改完成的总体周期及与传统方式的对比。

### 第五部分　实施效果：从案例成效到组织能力（约 10%—15%）

这一部分不要重复案例经过，而是汇总两个案例共同证明的价值。

#### 1. 研发交付价值

- 缩短代码和系统认知、需求分析及问题定位时间。
- 减少阶段之间的信息搬运和重复整理。
- 通过自动验证、失败修复和独立审查提高任务闭环能力。

#### 2. 质量与风险价值

- 将测试与代码审核前移到每次变更。
- 形成需求、设计、代码、测试、审查和交付之间的证据链。
- 关键风险操作由人员确认，避免把自动化等同于无人负责。

#### 3. 组织能力价值

- 将知识、Skill、Rule、流程模板和评价任务转化为组织资产。
- 新项目可以复用已验证的流程，不需要每个团队重新摸索。
- 模型和工具可以替换，组织能力不依赖单一厂商或单一产品。

#### 4. 推荐成效指标

采用“任务质量 + 安全 + 稳定性 + 人工投入 + 成本”的组合，不以代码生成率或调用次数作为核心成效：

- 任务完成率、一次通过率、失败率和人工接管率。
- 交付周期、等待时间和人工投入。
- 测试通过率、覆盖率及缺陷发现阶段。
- 代码审核有效问题率、采纳率和高风险问题拦截数量。
- MCP 调用成功率、权限拒绝和越界操作拦截情况。
- 模型、算力和平台运行成本。

### 第六部分　风险控制：安全、合规与责任边界（约 10%—15%）

直接对应活动要求中的“如何保障安全、合规与可控”。

#### 1. 数据边界

- 对源码、需求、设计、测试和运行数据实施分类分级。
- 采用上下文最小化、脱敏和外发限制。
- 敏感代码和数据优先在自建或专属受控环境中处理。

#### 2. 权限和执行边界

- MCP 执行身份映射、最小权限和限时授权。
- 外部系统凭据集中托管，不进入模型上下文或代码。
- 代码修改在隔离分支和安全沙箱内进行。
- 对终端、网络、文件、工具和参数设置白名单、资源限额及禁止事项。

#### 3. 质量和责任边界

- AI 输出必须经过测试、独立审核和人工验收。
- 核心代码合并、生产发布、生产数据和权限策略变更由授权人员决策。
- 对持续失败、信息不足和高风险任务设置人工接管和终止条件。

#### 4. 审计和运营边界

- 记录任务、上下文来源、模型、工具、参数、产物、证据、审批和处置结果。
- 对模型、Agent、Skill、Rule、连接器和流程模板实施版本与生命周期管理。
- 通过真实任务评价决定能力的优化、推广、降级或退出。

### 第七部分　创新特点与推广价值（约 5%—10%）

建议归纳为四点：

1. **从功能接入到流程重构**：不是在若干环节增加 AI 按钮，而是建立连续任务状态和完整交付闭环。
2. **Pi 执行与 MCP 连接解耦**：研发决策、Agent 编排与外部工具访问分层，便于模型、工具和平台替换。
3. **自主执行与人工责任统一**：依据风险配置自主程度，关键责任节点保持不变。
4. **研发交付与能力运营双闭环**：每次任务既交付研发成果，也生成可复用、可评价的组织能力资产。

推广路径：

- 从低风险、结果容易验证的研发任务开始。
- 先在少量项目中验证任务完成、质量、安全和成本。
- 将验证有效的能力扩展至需求、设计、开发、测试、发布和运行反馈。
- 对效果不稳定、风险过高或治理成本过大的能力及时降级或退出。

### 第八部分　结语（约 5%）

建议结尾观点：

> AI 研发的真正价值，不是生成更多代码，而是以可控方式完成更多真实研发任务。本项目通过 Pi 的自主执行、MCP 的受控连接、人工责任检查点和真实任务评价，使 AI 从个人辅助工具逐步成为可执行、可验证、可追溯、可持续改进的金融科技研发能力。

## 四、其他通用案例备选

以下案例具有较强通用性，但只有在存在真实实践和数据时才写入正文；否则作为未来推广方向。

### 备选案例一：存量系统单元测试资产构建

适用问题：

- 存量代码缺少测试，修改依赖人工回归。

工作流：

> 代码分析 → 测试范围识别 → 用例设计 → 测试代码生成 → 编译运行 → 失败修复 → 用例独立审核 → 覆盖率分析

可证明的价值：

- 测试数量和覆盖率提升。
- 关键缺陷或边界问题提前发现。
- 后续代码修改具备稳定回归基础。

该场景与内部已有的 Pi 单元测试多 Agent 探索较为接近，可以作为案例一中的测试环节，或在篇幅允许时作为简短补充案例。

### 备选案例二：缺陷修复闭环

适用问题：

- 缺陷信息、代码、日志、测试和发布记录分散，定位与验证时间较长。

工作流：

> 工单触发 → MCP 获取日志、代码和变更历史 → Pi 复现与根因分析 → 生成修复方案 → 修改代码 → 回归测试 → 独立审核 → 人工合并

可证明的价值：

- 缺陷平均定位和修复时间变化。
- 一次修复成功率及回归缺陷情况。
- 人工介入环节与 AI 自主完成比例。

### 备选案例三：变更影响分析与发布材料生成

适用问题：

- 发布前需要人工汇总代码变更、影响模块、测试证据、风险和回滚方案。

工作流：

> 读取需求与代码差异 → 分析依赖和影响范围 → 汇总测试与审查结果 → 生成变更说明、风险清单和回滚方案 → 人工审批

可证明的价值：

- 发布材料准备时间。
- 影响范围遗漏率和退回修改次数。
- 变更、测试和发布证据的一致性。
