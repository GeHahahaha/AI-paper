正式申报稿暂不公开业务系统、模型、工具和平台真实名称，统一采用功能性匿名名称：

- **已投入使用**：提交触发和定时全量扫描的 AI 代码审核平台，以及 Git、ONES、Jira 等外部研发平台的受控连接能力。

### 4. 案例组合

正文建议重点写两个完整案例：

1. **深度案例：某存量金融业务系统的需求逆向与整系统重构。** 在仅有源码及有限资料的基础上，完成整套系统的需求恢复、重新设计、重写、测试、审核、验收和上线运行，证明工作流能够承接上下文缺失、跨阶段、复杂度较高的完整研发任务。
2. **安全案例：开源组件漏洞的全机构排查与试点整改。** 根据外部单位同步的不同严重程度安全漏洞，在全机构范围排查数十个项目，并对选定试点项目完成整改、测试、代码审核和证据化交付。

两个案例均有真实执行记录。案例一用于证明复杂系统整系统重构和完整交付能力；案例二用于证明工作流能够跨项目识别安全影响并完成试点整改。具体数量和效果数据在正文写作阶段补齐。

提交触发的 AI 代码审核平台不是独立案例，而是工作流中贯穿开发、漏洞整改和交付验收的公共质量节点。单元测试资产构建、缺陷修复闭环等场景可以作为辅助说明或后续推广方向。

## 二、摘要写作要点

摘要建议按照“问题—方案—案例—价值—边界”组织，不在摘要中罗列行业趋势。

1. **问题**：当前 AI 在研发中的应用多以代码补全、问答、测试生成等分散工具为主，缺少连续任务状态、跨平台协同、统一验证和安全治理。
2. **方案**：构建以智能执行中枢、受控连接层、人工检查点和安全治理为核心的 AI 研发工作流。
3. **案例**：将工作流用于某存量金融业务系统的需求逆向与整系统重构，以及开源组件漏洞的全机构排查与试点整改；提交触发和定时扫描的 AI 代码审核作为两个案例共用的质量节点。
4. **价值**：提升复杂系统认知、研发交付、测试验证和代码质量控制能力，使 AI 从单点辅助工具转变为组织级研发能力。
5. **边界**：核心代码合并、生产发布、生产数据和权限变更仍由授权人员决策，AI 全过程留痕并接受真实任务评价。

**建议关键词：**

> 人工智能；AI 研发工作流；多智能体协同；代码审核；研发效能；自主可控

## 三、正文大纲

现有活动材料未明确正文字数，以下给出合计为 100% 的推荐比例。若最终正文约 5,000 字，可按比例换算并在成稿时小幅调整。

### 第一部分　应用背景：从分散辅助走向受控交付（约 10%）

#### 1. 金融科技研发面临的现实问题

- 研发过程涉及需求、设计、代码、测试、质量、发布和运维等多个平台，信息容易割裂。
- AI 已进入多个研发环节，但大多是开发人员主动发起的一次性问答或生成任务。
- AI 生成的代码、测试和分析结果缺少连续上下文、统一验收标准、独立审查和完整证据。
- Agent 接入代码、终端和外部系统后，数据泄露、权限误用、工具滥用和错误执行风险进一步扩大。

#### 2. 单点工具无法解决的问题

- 代码生成速度提升不等于研发任务整体交付效率提升。
- 不同人员分别使用 AI，形成的提示词、规则和经验难以复用。
- 缺少从需求到运行反馈的完整闭环，失败无法系统复盘，能力也难以持续改进。
- 自动化程度越高，越需要清晰的人机责任和安全控制。

#### 3. 项目建设目标

建设一套不整体替换既有研发平台的 AI 研发工作流，使 AI 能够：

- 在任务级上下文中连续工作，而非停留在单次对话。
- 连接既有工具和数据，但不绕过现有权限与审批体系。
- 自主完成低风险、可验证任务，在关键风险节点交由人员决策。
- 形成测试、审查、决策和运行证据，使结果可验证、过程可追溯。

本部分结尾提出核心问题：

> 如何在保持金融研发责任体系和安全边界不变的前提下，让 AI 从代码辅助工具转变为能够承接完整研发任务的受控执行体系？

### 第二部分　技术方案：智能执行、受控连接、人机协同（约 25%）

#### 1. 总体架构

插入正文 **图 1《AI 增强研发全生命周期总图》**，工程源文件为《图5_AI增强研发全生命周期总图.drawio》。

以传统研发生命周期为主轴：

> 任务受理 → 需求分析 → 方案设计 → 开发实施 → 测试验证 → 审查验收 → 发布交付 → 运行反馈

说明四个纵向层次：

1. 人工责任与检查点。
2. 智能执行中枢自主执行。
3. 受控连接层连接外部系统。
4. 数据、权限、执行、质量、审计和评价治理。

明确总体架构边界：

- 既有项目管理、代码、测试和发布平台继续保存正式任务状态、审批结论和责任关系。
- 智能执行中枢维护单个智能任务的执行上下文、步骤状态和证据，不替代既有研发管理系统。
- 受控连接桥接组件或内部连接器将经过批准的外部能力映射为可调用工具，并执行权限、参数和审计控制。
- 生成式 AI 负责分析、生成和解释，编译、测试、覆盖率、扫描及其他强制门禁由确定性程序判定。

#### 2. 智能执行中枢的任务执行机制

插入正文 **图 2《智能执行中枢任务执行子流程》**，工程源文件为《图6_Pi自主任务执行子流程.drawio》。

按八个步骤介绍：

1. 建立任务契约：目标、范围、验收标准、风险等级和审批策略。
2. 构建任务上下文：通过受控连接层获取需求、代码、历史、测试和运行信息。
3. 规划与 Agent 编排：拆分步骤，选择专业 Agent、模型、工具和质量阈值。
4. 隔离环境执行：在受控分支与沙箱中实施代码、配置和文档变更。
5. 自动验证与修复：执行测试、静态和安全检查，失败后自动归因、修复和复测。
6. 独立审查与整改：以独立上下文检查正确性、安全性、合规性和变更影响。
7. 证据化交付：汇总 PR、变更说明、测试、审查、风险与回滚材料。
8. 反馈与能力沉淀：将运行反馈和失败案例沉淀为知识、Skill、Rule、流程模板及评价任务。

每个可复用节点采用统一任务契约：

> 节点 = 输入工件 + Agent 角色 + Skill/Rule + 工具白名单 + 结构化输出 + 确定性校验 + 人工审批 + 审计证据 + 成功/返工路由

任务契约不要求正文罗列全部技术字段，但应说明每个节点都具有明确输入、正式产物、质量门禁、责任人和失败去向，避免 Agent 只完成一次性生成而无法进入既有研发流程。

结构化交接机制：

- 不同职责的 Agent 使用相互隔离的任务会话，开发、测试和审查不依赖同一段完整对话历史。
- 上下游通过受控的结构化交付物传递上下文，例如需求规格、实施计划、代码差异、测试报告和审查结论。
- 每份交付物标明输入来源、任务范围、版本、输出格式、完成条件及人工确认状态。
- 长任务保留节点状态、交付物和检查点；中断恢复能力只按实际运行证据描述，不将设计能力直接写成既有成果。

证据驱动的完成条件：

> “生成了文字或代码”不等于任务完成。节点完成必须由实际变更、工具执行、可复现验证、独立审查和人工责任状态共同证明。

- 存在与任务目标对应的代码、测试、配置或文档变更。
- 保留关键工具调用、执行命令、返回结果和异常处置记录。
- 编译、测试、覆盖率或扫描结果能够复现，并满足任务契约约定的质量门禁。
- 独立审查结论和阻断问题处置完成；需要人工确认的节点具有明确的审批或验收状态。

案例一中的多智能体质量门禁工作流将上述流程具体化为四阶段质量门禁：

1. 需求与设计门禁。
2. TDD 开发门禁。
3. 集成验证门禁。
4. 交付提交门禁。

每个阶段都有交付物、独立审查和失败回退条件，审查不通过不能进入下一阶段。

失败后不简单从头重跑，而是根据原因定向返回相应节点：

- 需求语义或验收条件不明确，返回需求分析和人工确认。
- 架构、接口或兼容性问题，返回方案设计。
- 实现、测试或代码质量问题，返回开发及相应测试节点。
- 超过重试阈值、连续失败或风险升级时，转由人员接管并决定继续、降级或终止。

#### 3. 智能体编排机制

插入正文 **图 3《智能体编排架构》**，工程源文件为《图7_Pi智能体编排架构.drawio》。

重点说明：

- 主控 Agent 维护智能任务内部的执行状态、依赖、检查点、异常恢复和结果汇总；该状态仅表示智能任务步骤，不代表正式项目状态，审批结论和责任归属仍以既有研发平台记录为准。
- 需求、架构、开发、测试、审查、交付及运维 Agent 按角色分工。
- 所有 Agent 共享经过权限控制的任务上下文、计划、产物和证据。
- 策略与模型路由层根据任务风险、模型能力、数据敏感等级、稳定性和成本选择模型。
- 审查 Agent 使用独立上下文，避免开发与审查逻辑完全同源。

#### 4. 受控连接层外部交互机制

插入正文 **图 4《受控连接层外部交互与治理子图》**，工程源文件为《图8_MCP外部交互与治理子图.drawio》。

受控连接调用链包括：

1. 工具发现与选择。
2. 身份映射与最小权限授权。
3. 上下文和参数校验。
4. 连接器受控执行。
5. 结果标准化与完整性校验。
6. 调用审计及任务状态回写。

明确受控连接层的定位：

- 受控连接层负责连接和控制，不负责研发方案决策。
- 受控连接层不被描述为智能执行中枢原生的完整工作流能力，而是通过桥接组件、扩展或内部连接器形成受控工具接入。
- 外部系统凭据由连接层或既有凭据系统托管，不进入 Agent 长期上下文。
- 高风险写操作进入人工授权检查点。

#### 5. 贯穿开发与交付的 AI 代码质量审核节点

代码审核平台作为工作流的标准质量门禁，不单独包装成案例。

运行方式：

1. 智能执行中枢或开发人员完成代码提交、整改提交或合并请求。
2. 代码仓库事件自动触发 AI 代码审核平台。
3. 平台通过受控连接层获取代码差异、相关文件、任务背景、项目规则和历史问题。
4. 审查 Agent 从正确性、安全性、并发与内存安全、空指针、边界情况、异常处理、可维护性、测试充分性和变更影响等维度审核。
5. 平台将问题分级，给出位置、依据、影响和修改建议，并回写提交或合并请求。
6. 严重问题返回开发或漏洞整改环节，一般问题由人员确认处置。
7. 处置结果反哺审核 Rule、问题模式、评价任务和模型选择。

该节点在两个案例中承担相同职责：

- 在案例一的整系统重写中，审核新实现是否偏离确认后的需求和设计。
- 在组件漏洞整改中，审核漏洞是否真正消除、升级是否引入兼容性和安全问题。
- 在日常研发中，每次代码提交均可触发相同的质量审核机制，体现平台化和规模化基础。

#### 6. 两个闭环

- **研发交付闭环**：任务 → 需求 → 设计 → 开发 → 测试 → 审查 → 交付 → 运行反馈。
- **能力运营闭环**：运行记录 → 成效评价 → 失败复盘 → 能力更新 → 再验证 → 推广、降级或退出。

### 第三部分　实践案例一：某存量金融业务系统的需求逆向与整系统重构（约 18%）

该案例用于证明工作流具有跨阶段处理复杂研发任务的能力。

#### 1. 案例背景

- 某存量金融业务系统长期演进，原始人员和设计知识不足，需求理解和质量保障较依赖个人经验。
- 保留了源码及有限项目资料，但原始需求存在缺漏、不准确或与代码实际行为不一致的情况。
- 传统方式需要研发人员逐文件阅读代码、人工推断业务逻辑，修改影响范围和回归风险难以判断。
- 原系统代码规模约 3 万行。项目目标不是简单让 AI 生成代码，而是恢复可确认的需求和系统认知，并在质量门禁约束下完成整套系统的重新设计与重写。
- 需求逆向、设计、开发、单元测试、集成测试、代码审核和交付门禁均已完成，系统通过内部验收并已上线正常运行。

#### 2. 工作流实施过程

建议按以下顺序写成一个完整故事：

1. **任务受理**：明确需要恢复的业务能力、系统边界、验收范围和不可触碰的安全边界。
2. **代码图谱与上下文构建**：将大型代码库结构化为模块、调用和依赖关系，Agent 按需查询相关代码，避免一次加载全部源码造成上下文溢出。
3. **需求逆向**：通过需求逆向提取命令，从代码中提取业务规则、校验逻辑和交互流程，形成需求规格初稿。
4. **需求独立审查**：需求审查 Agent 从完整性、可测性、安全性等维度审核；将“代码事实”“模型推断”和“待业务确认事项”分开，由人员确认关键语义。
5. **TDD RED 阶段**：基于确认后的需求规格先编写单元测试，并由独立 RED 审查 Agent 检查覆盖范围、边界条件和反模式。
6. **TDD GREEN 阶段**：开发 Agent 编写实现代码并迭代至测试通过，案例设置单元测试覆盖率不低于 80% 的质量门禁。
7. **集成验证**：设计跨模块集成测试方案，由独立审查 Agent 检查场景和业务规则覆盖，并通过浏览器自动化执行冒烟测试。
8. **失败修复循环**：发现问题后执行“补测试—修代码—重跑全量”，存在 P0/P1 问题则回退整改并重新审查。
9. **独立代码审核**：提交触发的代码审核平台检查实现正确性、安全性、异常处理、边界条件及项目规则。
10. **交付门禁与资产沉淀**：单元测试、集成测试和覆盖率全部达标后提交交付，并归档需求、审查、测试、代码和决策证据。

#### 3. 案例交付资产

案例结果不只体现为代码修改，建议按照以下四类组织并核验实际交付物：

1. **需求与规则资产**：需求规格、业务规则、事实与推断区分、待确认事项及人工确认记录。
2. **设计与接口资产**：系统结构、模块职责、调用关系、接口、数据对象和关键设计决策。
3. **实现与验证资产**：实现代码、单元测试、集成测试、覆盖率报告、执行记录和独立审查报告。
4. **交付与运维资产**：变更说明、部署或操作说明、风险与回滚材料、维护交接和后续演进建议。

正式成文时只列入能够提供脱敏证据的资产；尚未形成或未完成验收的材料放入待补清单，不作为既有成果。

#### 4. 案例创新点

- 不是让 AI 对源码做一次性总结，而是通过完整工作流将源码认知转化为需求、设计、代码、测试和审查证据。
- 对逆向得到的需求区分“事实、推断和待确认项”，控制大模型对业务语义的误判。
- 采用“AI 执行 + 流程约束 + 独立审查”的多智能体质量门禁方法，质量检查被前置并强制嵌入各阶段。
- 开发 Agent 与审查 Agent 使用独立上下文，避免同一执行逻辑同时充当运动员和裁判。
- 重新设计与实现过程由 TDD、80% 案例覆盖率门禁、集成验证和提交触发的代码审核共同约束。
- 代码图谱使大型代码库能够按需检索，为后续受控上下文连接机制提供了实践基础。
- 本轮实践完成整系统重构并形成可维护的需求、架构、测试和交付资产，降低知识再次流失的风险。

#### 5. 需要补齐的数据

- 系统规模：代码量、模块数、接口数、核心业务链路数。
- 逆向成果：恢复的需求、规则、流程、接口或数据对象数量。
- 测试效果：单元测试数量、80% 覆盖率的计算范围、集成场景和发现问题数量。
- 现有投入数据：项目历时三周，人工投入约五人天；需要补充统计起止、人员角色和工作内容。
- 运行效果：上线后的稳定运行周期、问题反馈和后续维护情况。
- 资产沉淀：审查 Agent、开发技能和流程命令的准确数量；当前材料存在三类与四类审查 Agent 的口径差异。
- 成本数据：模型 Token 与 credits 暂不直接用于成效结论，除非能够补充统一成本和对照口径。

### 第四部分　实践案例二：开源组件漏洞全机构排查与试点整改（约 17%）

该案例来自已经执行的安全整改任务，用于证明工作流能够在收到外部单位同步的安全漏洞后，在全机构范围完成项目排查，并对选定试点项目完成整改实施、测试审核、人工审批和证据化闭环。

#### 1. 案例背景

- 金融科技系统大量使用开源组件，每次收到的漏洞类型和严重程度不同，均需要快速判断影响范围和处置优先级。
- 单次任务需要在全机构数十个项目中开展排查，识别直接依赖、间接依赖及受影响版本。
- 传统处置需要人工查询依赖清单、联系项目负责人、分析兼容性并逐个项目整改。
- 项目数量较多时，影响范围识别、整改进度和残余风险容易分散，难以形成统一证据。
- 简单批量升级可能造成构建失败、接口不兼容或业务回归，不能只根据组件版本自动修改。

#### 2. 工作流实施过程

1. **任务触发**：安全平台、漏洞通告或人员发起应急整改任务，明确漏洞严重度、处置时限和验收标准。
2. **影响范围识别**：受控连接层连接组件清单、依赖扫描和代码仓库，智能执行中枢识别直接依赖、间接依赖、受影响项目及版本。
3. **兼容性分析**：架构和开发 Agent 分析可用修复版本、接口变化、项目约束和潜在影响。
4. **项目级整改计划**：智能执行中枢按项目风险、依赖关系和负责人生成整改任务，配置测试范围和人工检查点。
5. **隔离环境整改**：开发 Agent 在各项目受控分支中升级组件并调整相关代码、配置和构建文件。
6. **自动测试与失败修复**：运行构建、单元、集成和关键回归测试；失败后自动归因、调整方案并复测。
7. **提交触发 AI 代码审核**：每次整改提交自动进入代码质量审核节点，检查漏洞是否消除、升级是否完整、兼容性和安全风险是否可接受。
8. **证据化交付**：生成项目清单、影响分析、整改 PR、测试报告、审核结果、残余风险和发布建议。
9. **人工审批与发布**：项目负责人审批合并和发布，高风险或无法确认兼容性的项目转人工专项处理；试点项目完成整改闭环。
10. **持续跟踪与沉淀**：受控连接层回写排查与整改状态，工作流持续跟踪其他项目，并将漏洞模式、兼容问题和升级经验沉淀为知识、Rule 和评价任务。

#### 3. 案例创新点

- 将漏洞通告、组件清单、代码仓库、测试、代码审核和发布证据串成一条完整工作流。
- 智能执行中枢可以按项目拆分并行任务，但每个项目独立测试、审核和审批，兼顾效率与风险隔离。
- 代码审核平台不再只是日常辅助工具，而是漏洞整改流程中的标准质量检查点。
- 最终输出不仅是代码修改，还包括受影响范围、整改状态、验证证据和残余风险。
- 模型、扫描工具和代码平台通过受控连接层解耦，可按环境和安全等级替换。

#### 4. 需要补齐的数据

- 漏洞类型、严重等级、处置时限及选取该案例的原因。
- 排查项目数、受影响项目数、完成试点整改项目数、直接和间接依赖数量；当前规模为数十个项目，正式稿补充准确数字。
- 从任务触发到完成影响范围识别的时间。
- 自动生成或辅助完成的整改分支、提交和 PR 数量。
- 构建、测试和代码审核的一次通过率及失败原因分布。
- 人工介入项目数、兼容性问题数和残余风险。
- 从漏洞通告到整改完成的总体周期及与传统方式的对比。

### 第五部分　实施效果：从案例成效到组织能力（约 12%）

这一部分不要重复案例经过，而是汇总两个案例共同证明的价值。

#### 1. 研发交付价值

- 缩短代码和系统认知、需求分析及问题定位时间。
- 减少阶段之间的信息搬运和重复整理。
- 通过自动验证、失败修复和独立审查提高任务闭环能力。

#### 2. 质量与风险价值

- 将测试与代码审核前移到每次变更。
- 形成需求、设计、代码、测试、审查和交付之间的证据链。
- 关键风险操作由人员确认，避免把自动化等同于无人负责。

#### 3. 组织能力价值

- 将知识、Skill、Rule、流程模板和评价任务转化为组织资产。
- 新项目可以复用已验证的流程，不需要每个团队重新摸索。
- 模型和工具可以替换，组织能力不依赖单一厂商或单一产品。

#### 4. 推荐成效指标

采用“任务质量 + 安全 + 稳定性 + 人工投入 + 成本”的组合，不以代码生成率或调用次数作为核心成效：

所有正式成效数字均需同时说明“前后对比、统计周期、样本范围和计算口径”；暂时缺少可比基线时，使用可核验的绝对数据和匿名化典型案例，不推导未经验证的提升比例。

- 任务完成率、一次通过率、失败率和人工接管率。
- 交付周期、等待时间和人工投入。
- 测试通过率、覆盖率及缺陷发现阶段。
- 代码审核有效问题率、采纳率和高风险问题拦截数量。
- 受控连接调用成功率、权限拒绝和越界操作拦截情况。
- 模型、算力和平台运行成本。

#### 5. 建议效果表格

**表 1：案例改造前后状态对比**

- 对比维度：需求来源与完整性、设计文档、测试约束、独立审查、问题追溯和交付资产。
- 表格字段：对比维度、改造前状态、改造后状态、判断依据及证据编号。
- 没有可靠基线时只比较可核验的状态变化，不填写推测性的提升比例。

**表 2：实施效果及证据索引**

- 表格字段：指标或结论、统计结果、统计周期、样本范围、计算口径、证据来源及公开方式。
- 证据来源可以包括测试报告、覆盖率报告、审查记录、代码提交、验收材料和脱敏运行日志。
- 正文中的每项关键效果均应能够定位到对应证据，避免效果描述与附件材料脱节。

### 第六部分　风险控制：安全、合规与责任边界（约 10%）

直接对应活动要求中的“如何保障安全、合规与可控”。

#### 1. 数据边界

- 对源码、需求、设计、测试和运行数据实施分类分级。
- 采用上下文最小化、脱敏和外发限制。
- 敏感代码和数据优先在自建或专属受控环境中处理。

#### 2. 跨环境协作检查

当前任务采用单一网络环境运行：要么全部在内网受控环境完成，要么全部在外部环境完成，不进行跨网络直接流转。正式成文时说明以下边界：

- 内网受控环境可在授权范围内使用原始内部材料，并执行既有访问控制和审计要求。
- 外部环境使用的需求、代码、文档、配置和测试材料全部先行脱敏。
- 不同网络环境之间不直接传递未经处理的源码、业务数据、账号凭据或安全配置。
- 模型服务、任务日志、缓存及中间产物的保存位置、访问范围和留存周期。

正文不出现“将内部材料直接带到外部环境”等可能引发合规疑问的表述，也不补写实际不存在的审批或安全措施。

#### 3. 权限和执行边界

- 受控连接层执行身份映射、最小权限和限时授权。
- 外部系统凭据集中托管，不进入模型上下文或代码。
- 代码修改在隔离分支和安全沙箱内进行。
- 对终端、网络、文件、工具和参数设置白名单、资源限额及禁止事项。

#### 4. 质量和责任边界

- AI 输出必须经过测试、独立审核和人工验收。
- 核心代码合并、生产发布、生产数据和权限策略变更由授权人员决策。
- 对持续失败、信息不足和高风险任务设置人工接管和终止条件。

#### 5. 审计和运营边界

- 记录任务、上下文来源、模型、工具、参数、产物、证据、审批和处置结果。
- 对模型、Agent、Skill、Rule、连接器和流程模板实施版本与生命周期管理。
- 通过真实任务评价决定能力的优化、推广、降级或退出。

#### 6. 能力资产与供应链边界

- 对 Skill、扩展、软件包、连接器及其依赖实施准入审查，未经批准的能力不得进入正式研发流程。
- 对模型、提示词、规则、工具和连接器进行版本锁定与变更记录，保证任务结果能够复现和追溯。
- 建立依赖清单、漏洞检查、紧急禁用和退出机制，发现高风险缺陷时能够及时停止相关能力。

### 第七部分　创新特点与推广价值（约 5%）

建议归纳为五点：

1. **从功能接入到流程重构**：不是在若干环节增加 AI 按钮，而是通过统一节点契约建立连续任务状态和完整交付闭环。
2. **执行与连接解耦**：智能执行、正式流程状态与外部工具访问分层，便于模型、工具和平台替换。
3. **生成式能力与确定性门禁结合**：AI 负责分析和生成，测试、扫描、阈值及人工审批共同约束结果。
4. **定向返工与人机责任统一**：依据失败原因返回需求、设计、开发或测试节点，关键责任节点保持不变。
5. **研发交付与能力运营双闭环**：每次任务既交付研发成果，也生成可复用、可评价的组织能力资产。

推广路径：

- 从低风险、结果容易验证的研发任务开始。
- 先在少量项目中验证任务完成、质量、安全和成本。
- 将验证有效的能力扩展至需求、设计、开发、测试、发布和运行反馈。
- 对效果不稳定、风险过高或治理成本过大的能力及时降级或退出。

### 第八部分　结语（约 3%）

建议结尾观点：

> AI 研发的真正价值，不是生成更多代码，而是以可控方式完成更多真实研发任务。本项目通过智能执行中枢的自主执行、受控连接层的外部协同、人工责任检查点和真实任务评价，使 AI 从个人辅助工具逐步成为可执行、可验证、可追溯、可持续改进的金融科技研发能力。

## 四、其他通用案例备选

以下案例具有较强通用性，但只有在存在真实实践和数据时才写入正文；否则作为未来推广方向。

### 备选案例一：存量系统单元测试资产构建

适用问题：

- 存量代码缺少测试，修改依赖人工回归。

工作流：

> 代码分析 → 测试范围识别 → 用例设计 → 测试代码生成 → 编译运行 → 失败修复 → 用例独立审核 → 覆盖率分析

可证明的价值：

- 测试数量和覆盖率提升。
- 关键缺陷或边界问题提前发现。
- 后续代码修改具备稳定回归基础。

该场景与内部已有的单元测试多 Agent 探索较为接近，可以作为案例一中的测试环节，或在篇幅允许时作为简短补充案例。

### 备选案例二：缺陷修复闭环

适用问题：

- 缺陷信息、代码、日志、测试和发布记录分散，定位与验证时间较长。

工作流：

> 工单触发 → 受控连接层获取日志、代码和变更历史 → 智能执行中枢复现与根因分析 → 生成修复方案 → 修改代码 → 回归测试 → 独立审核 → 人工合并

可证明的价值：

- 缺陷平均定位和修复时间变化。
- 一次修复成功率及回归缺陷情况。
- 人工介入环节与 AI 自主完成比例。

### 备选案例三：变更影响分析与发布材料生成

适用问题：

- 发布前需要人工汇总代码变更、影响模块、测试证据、风险和回滚方案。

工作流：

> 读取需求与代码差异 → 分析依赖和影响范围 → 汇总测试与审查结果 → 生成变更说明、风险清单和回滚方案 → 人工审批

可证明的价值：

- 发布材料准备时间。
- 影响范围遗漏率和退回修改次数。
- 变更、测试和发布证据的一致性。

- 需求、设计、开发、单元测试、集成测试、代码审核和交付门禁全部完成，系统通过内部验收并上线正常运行。
- 已实施需求、TDD、集成验证和交付四阶段质量门禁，案例单元测试覆盖率达到 80% 门禁。
- 已采用开发与审查分离、独立上下文审查、P0/P1 问题回退和浏览器自动化冒烟测试。
- 已形成三周周期、约五人天人工投入等初步实践数据。
- 已执行开源组件漏洞的全机构项目排查，项目规模为数十个，并对选定试点项目完成整改；保留了真实分支、提交、PR、测试报告和代码审核记录。
- 已建设 AI 代码审核平台，可通过 Git 代码提交差异触发审核，也可配置定时全量扫描；平台已经通过受控连接层获取相关代码信息。
- 已探索由智能执行中枢编排的单元测试设计、生成、审核和覆盖率报告工作流。

### 已贯通、运行成熟度待量化的内容

- 智能执行中枢可以在需求、设计、开发、测试、审查和交付等环节配置执行节点，整体研发流程已经贯通。
- 受控连接层已经接入 Git、ONES、Jira 等研发平台，并支持代码、任务和状态信息的获取与回写。
- 已贯通的工作流保留过程状态和证据，具备回放能力；正式稿需要选取代表性任务整理可公开的回放记录。
- 各环节是否达到长期稳定运行水平尚缺统一统计，应以成功率、失败类型、人工介入和运行周期等数据量化，不作笼统判断。

### 需要项目组补充口径后才能写成正式成果的内容

- 三周、五人天和 80% 覆盖率的统计范围与计算口径。
- 审查 Agent 数量、开发技能数量和流程命令数量的统一口径。
- 两个案例的需求、规则、测试、缺陷、项目和整改数量等准确数据。
- 代码审核平台的项目数、提交数、审核问题数、采纳率、高风险问题数、审核规则和阻断策略。
- 各执行环节的成功率、运行周期、失败类型和人工介入情况，用于判断稳定运行水平。
- 代表性任务回放材料的脱敏范围，包括节点输入输出、工具调用、检查点、测试审查结果和人工确认记录。
- 最终允许公开的模型、工具、平台和业务名称；在确认前统一使用匿名功能名称。
- 所有成效数字、比例、节约时间、缺陷数量和成本数据。

### 不应直接写入的内容

- 将目标架构或规划能力描述成已经全面落地。
- 因各环节稳定性数据尚未汇总，就否定已经贯通的整体流程；或反过来把“流程已经贯通”写成“所有环节均已长期稳定运行”。
- 没有统计口径的“效率提升数倍”“缺陷大幅下降”等结论。
- “AI 全自动替代研发人员”“无人审批即可发布生产”等表述。
- 未经脱敏或未经确认可公开的业务系统、模型、工具、平台名称，以及源码、业务数据、人员信息或安全配置。
