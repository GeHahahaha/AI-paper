## 第一章 应用背景

### 1.1 金融科技研发的普遍协同难题

#### 要回答的问题

为什么已有代码助手和大模型之后，仍然需要一个工作流平台？

#### 建议论点

1. 研发跨越需求、设计、开发、测试、评审和交付，材料分散在人员、代码库和不同工具中；
2. 单次问答或代码生成只能解决局部问题，难以保持跨阶段目标一致；
3. 同一模型既生成又自我确认，容易遗漏边界条件或跳过工程步骤；
4. 金融系统要求结果可验证、过程可追溯、权限有边界、责任可落实；
5. 因此，需要将模型能力纳入既有研发责任体系，而不是追求无边界自动化。

### 1.2 存量系统问题是通用难题的集中体现

#### 案例引入方式

只用一段匿名描述引出案例，不提前展开全部细节：

> 某内部金融业务系统运行时间较长，代码规模较大、业务规则复杂，原始需求、设计和测试资料存在缺失或与实际代码不一致的情况。系统知识主要沉积在源代码和少数维护经验中，需求理解、变更影响分析和质量验证成本较高。

#### 需要强调的业务影响

- 业务规则难追溯，容易造成需求理解偏差；
- 变更影响范围难判断，增加系统稳定性风险；
- 测试资产不足，质量保障依赖人员经验；
- 文档缺失影响交接、维护与持续演进。

### 1.3 平台建设目标

1. 建立可编排的端到端研发工作流；
2. 通过角色分工降低同一模型自我确认带来的偏差；
3. 以代码变更、测试结果和评审结论作为交付证据；
4. 在关键业务语义、质量结论和正式交付环节保留人工责任；
5. 将真实实践中的角色、技能、命令、门禁和交付模板沉淀为组织资产。

## 第二章 AgentFlow 平台总体方案

### 2.1 设计理念

围绕四个关键词展开：

- **可编排**：复杂任务被拆解为职责和输入输出明确的节点；
- **可验证**：模型输出需要经过测试、审查和人工验收；
- **可恢复**：长流程中断后能够保存状态并从检查点继续；
- **可追溯**：任务、工具执行、交接材料和结论形成证据链。

### 2.2 平台总体架构

建议按五层描述：

1. **任务入口层**：创建任务、选择工作目录、配置工作流、查看运行状态；
2. **工作流编排层**：管理节点依赖、运行顺序、失败回退、迭代次数和人工暂停点；
3. **多智能体执行层**：需求、规划、开发、测试、评审、报告等角色独立执行；
4. **工具与资源层**：代码工作区、测试工具、浏览器验证、模型服务和受控知识材料；
5. **证据与治理层**：交接文档、运行日志、测试结果、评审结论、检查点和人工确认记录。

明确说明：AgentFlow 是报告的通用平台主体，案例只是其中一个验证场景。

### 2.3 角色体系

| 角色 | 主要输入 | 核心职责 | 主要输出 | 质量约束 |
| --- | --- | --- | --- | --- |
| 需求分析 Agent | 原始需求、代码、现有资料 | 提取业务行为、规则与待确认问题 | 需求规格初稿 | 不确定项显式标记，人工确认关键语义 |
| 规划 Agent | 需求规格、约束和工作区信息 | 制定实现、测试和验收计划 | 研发计划与风险清单 | 计划评审通过后进入实现 |
| 开发 Agent | 已确认需求与计划 | 编写测试、实现功能、修复问题 | 代码、单测、开发总结 | 必须有实际工具和测试证据 |
| 测试 Agent | 需求、实现和环境信息 | 设计并执行集成验证 | 测试方案与执行报告 | 覆盖主流程、异常和边界场景 |
| 评审 Agent | 需求、计划、代码和测试结果 | 独立审查完整性与质量 | PASS/FAIL 与问题清单 | 严重问题触发回退重修 |
| 报告 Agent | 各阶段交付物与证据 | 汇总交付和复盘材料 | 交付报告与资产清单 | 保留来源和人工确认状态 |

### 2.4 结构化交接机制

1. 各 Agent 使用独立会话，降低上下文污染；
2. 上下游以受控 Markdown 文档交接，不依赖完整聊天历史；
3. 每个节点明确输入来源、输出格式、完成条件和失败处理；
4. 关键产物关联任务、测试、评审和人工确认记录；
5. 长流程使用检查点与状态恢复，避免中断后从头执行。

## 第三章 通用研发工作流与可信机制

### 3.1 四阶段质量门禁闭环

#### 第一阶段：需求与设计

- 从任务说明、代码和已有材料中恢复需求；
- 输出业务规则、接口行为、边界条件、异常处理和待确认项；
- 由独立评审角色检查完整性、一致性、可测性和安全边界；
- 人员确认关键业务语义后才能进入开发。

#### 第二阶段：TDD 开发

- RED：根据已确认需求编写测试，证明测试能够暴露尚未实现或待修复行为；
- RED 审查：检查测试覆盖、边界情况、断言有效性和测试反模式；
- GREEN：完成实现并迭代至测试通过；
- REFACTOR：在行为受测试约束的条件下改善代码结构；
- 质量门禁：正式稿写入经确认的覆盖率标准，案例材料中采用的门禁为不低于 80%。

#### 第三阶段：集成验证

- 面向真实业务链路编写端到端测试方案；
- 覆盖跨模块主流程、异常分支和边界条件；
- 必要时通过浏览器自动化验证真实用户操作路径；
- 发现问题后进入“补测试—修代码—重跑全量”的闭环。

#### 第四阶段：交付沉淀

- 检查单元测试、集成测试、覆盖率和评审结论；
- 规范保存需求、设计、代码、测试、审查和交付记录；
- 由人员完成最终验收、代码合并和正式发布决策。

### 3.2 独立评审与失败回退

1. 开发和评审角色不共享完整对话上下文；
2. 评审角色仅依据原始需求、结构化产物、实际代码和测试证据判断；
3. 问题可分为阻断、严重和建议三级；
4. 存在阻断或严重问题时回退至对应节点，修复后重新审查；
5. 达到迭代边界仍未通过时暂停流程，由人员决定继续、调整或终止。

### 3.3 证据驱动交付

强调“有文字输出”不等于“任务完成”。完成条件至少包括：

- 实际代码或文档变更；
- 工具执行记录；
- 可复现的测试结果；
- 独立评审结论；
- 人工确认或验收状态。

### 3.4 人机协同边界

#### 平台适合承担

- 大规模代码阅读与结构梳理；
- 需求、计划、测试和文档初稿生成；
- 重复性实现、检查与问题修复；
- 多阶段材料整理和证据关联。

#### 人员必须负责

- 业务语义、范围和优先级确认；
- 高风险设计决策；
- 评审结论复核与例外处置；
- 代码合并、发布和生产操作；
- 安全、合规与最终交付责任。

## 第四章 平台建设与方法迁移

### 4.1 从生产探索到平台化能力

这一节承担“案例事实”与“AgentFlow 平台”之间的连接，推荐使用以下表达：

> 团队先在真实存量系统研发任务中验证了代码逆向、TDD、独立审查、集成验证和交付留痕等方法。实践证明方法有效后，再将分散的角色定义、审查标准、开发技能、流程命令和交付模板迁移到 AgentFlow，由平台统一完成编排、状态管理和证据保存。

必须避免将原始生产实践所使用的具体工具简单改名为 AgentFlow。若后续已在 AgentFlow 中对代表性任务完成重放或再次执行，可在正式稿中补充“平台验证范围、运行记录和结果”；否则使用“方法得到生产验证、能力完成平台化迁移”的表述。

### 4.2 迁移内容

| 生产实践中已验证的要素 | 在 AgentFlow 中的沉淀形式 |
| --- | --- |
| 需求逆向分析方法 | 需求分析角色、输入模板、需求规格输出模板 |
| 开发计划与任务拆分 | 规划节点、任务依赖和验收条件 |
| TDD 开发过程 | RED/GREEN/REFACTOR 节点或开发技能 |
| 独立质量审查 | 独立评审角色、问题等级和 PASS/FAIL 规则 |
| 集成测试与浏览器验证 | 测试节点、工具调用和执行报告 |
| 问题修复循环 | 失败回退、定向返工和迭代边界 |
| 交付资料归档 | Markdown 交接、运行快照和报告模板 |

### 4.3 平台实施步骤

1. 明确工作目录、可用工具、数据范围和人工责任点；
2. 将方法拆分为角色、节点、输入输出和门禁规则；
3. 配置独立会话、结构化交接和状态检查点；
4. 选取低风险、边界清晰的研发任务进行验证；
5. 根据失败记录和人工评审持续调整模板；
6. 固化通用能力，逐步推广到更多任务类型。

## 第五章 匿名生产案例：某存量金融业务系统改造

### 5.1 案例起点

#### 已有事实

- 系统属于运行多年的存量项目；
- 代码规模较大、业务逻辑复杂；
- 原始需求资料存在缺漏、描述不准确或与代码行为不一致；
- 需求理解和质量保障较依赖个人经验；
- 实践范围覆盖需求分析、功能开发、测试验证和交付沉淀。

#### 正式稿匿名口径

统一称为“某存量金融业务系统”或“某内部金融业务支撑系统”，不披露真实系统、业务对象、机构和人员信息。

### 5.2 第一步：从代码恢复需求与设计依据

1. 分析代码结构、模块职责、调用关系和接口边界；
2. 从实际代码行为中提取业务规则、校验逻辑和交互流程；
3. 区分“代码可直接证明的事实”“推断规则”和“待人工确认问题”；
4. 形成需求规格初稿和审查报告；
5. 由熟悉业务的人员逐条确认关键语义、补充缺失信息。

### 5.3 第二步：基于确认需求完成系统改造

1. 根据需求规格形成目标方案、任务计划和验收标准；
2. 以 TDD 方式先构建测试约束，再完成实现；
3. 通过独立审查检查测试覆盖、边界条件和实现一致性；
4. 在覆盖率门禁和测试全绿的条件下进入集成验证；
5. 对发现的问题执行“补测试—修实现—重新验证”。

“重写整套系统”还是“对目标范围进行重构改造”必须以项目真实范围为准。正式稿在未获得范围证明前，优先使用“系统改造”或“重构实现”，避免扩大成果口径。

### 5.4 第三步：集成验证与交付

- 编写覆盖跨模块流程的集成测试方案；
- 验证真实操作路径、异常场景和关键边界；
- 完成单元测试、集成测试、覆盖率和评审门禁检查；
- 形成需求、设计、接口、代码、测试、部署和交付说明；
- 由人员完成最终验收和正式交付决策。

### 5.5 案例交付资产

建议按四类组织：

1. **需求与规则资产**：需求规格、业务规则、待确认项及确认记录；
2. **设计与接口资产**：架构说明、模块设计、接口和数据说明；
3. **实现与验证资产**：代码、单元测试、集成测试、执行报告和评审报告；
4. **交付与运维资产**：部署说明、操作说明、运维交接和变更记录。

## 第六章 实施效果

### 6.1 可直接使用但仍需复核口径的事实

| 维度 | 案例材料中的信息 | 正式稿处理建议 |
| --- | --- | --- |
| 实施周期 | 历时 3 周 | 核对起止时间和工作范围后使用 |
| 人工投入 | 约 5 人天/“5 人/天” | 原始写法存在口径歧义，必须确认后使用 |
| 单元测试 | 覆盖率达到 80% 门禁要求 | 补充统计工具、模块范围和报告证据 |
| 质量流程 | 需求、单测、集成方案均经过独立审查 | 补充可脱敏的审查结论样例 |
| 测试范围 | 覆盖跨模块流程及多类异常场景 | 补充场景数或代表性场景 |
| 资产沉淀 | 形成审查角色、开发技能和流程命令 | 原材料中的角色数量表述需统一后再写具体数字 |
| 文档资产 | 形成需求、审查、测试和交付材料 | 补充最终目录和文档数量 |

模型名称、调用量和积分消耗不是本报告的核心成效，除非比赛要求说明技术资源，否则不放入正文主线。

### 6.2 质量价值

- 通过代码逆向和独立审查减少需求歧义与遗漏；
- 通过 TDD 和覆盖率门禁将系统理解转化为可执行验证；
- 通过集成测试覆盖跨模块业务链路与异常场景；
- 通过失败回退避免问题在阶段之间无约束传递；
- 通过结构化交付降低系统知识继续依赖个别人员的风险。

### 6.3 效率与组织价值

- 人员从重复代码阅读、材料整理和常规实现中释放出来，集中处理关键业务决策；
- 工作流、角色和审查清单可以跨任务复用，边际实施成本逐步降低；
- 新成员可通过需求、测试和交付材料建立系统认知；
- 实践方法迁移为 AgentFlow 平台资产后，可扩展至更多研发场景。

### 6.4 效果表述边界

正式稿不使用未经统计支持的“效率提升 XX%”“成本下降 XX%”等结论。若无法取得改造前基线，采用“真实任务—交付产物—测试结果—人工验收”证据链说明成效。

## 第七章 风险控制与合规治理

### 7.1 数据与代码边界

- 仅处理经过授权的代码、文档、配置和测试材料；
- 对真实业务数据、账号、密钥和机构信息进行分级、脱敏或替换；
- 按最小必要原则提供上下文，避免一次性加载无关代码和资料；
- 正式申报材料中的截图、日志和案例细节需要经过脱敏审查。

### 7.2 跨环境协作边界

生产案例材料中存在跨环境协作描述，这是正式申报前必须核实的风险点。正文应基于真实制度与操作说明：

- 哪些材料可以离开受控环境；
- 是否完成审批、脱敏和安全检查；
- 是否存在禁止外传的源码、业务数据或配置；
- 模型服务、日志保存和数据留存如何管理。

未经确认，不写“将内部材料直接带到外部环境”等可能引发合规疑问的表述，也不能虚构不存在的安全措施。

### 7.3 权限与操作边界

- Agent 仅获得完成当前任务所需的目录和工具权限；
- 不允许直接修改生产数据、执行生产指令或调整生产权限；
- 代码合并、版本发布和生产部署由既有人工流程控制；
- 高风险工具执行设置人工确认点和明确的允许范围。

### 7.4 质量与责任边界

- 模型输出不得直接视为业务事实；
- 需求、设计和业务规则由人员确认；
- 代码必须通过编译、测试、独立评审和人工验收；
- 自动评审结果由人员复核，异常情况允许人工暂停或终止流程。

### 7.5 审计与追溯

留存任务输入、Agent 输出、工具事件、代码变更、测试结果、评审结论、检查点和人工处置记录，形成从需求到交付的证据链。

## 第八章 创新点与推广价值

### 8.1 从单点工具到可编排平台

将需求、开发、测试、评审和交付组织为可配置工作流，使人工智能能力覆盖连续工程过程，而不是停留在单次生成。

### 8.2 开发与评审相互独立

独立会话、结构化输入和标准化审查清单降低“同一模型既执行又自证正确”的风险，并支持明确的失败回退。

### 8.3 从生成结果到证据驱动交付

以实际代码变更、测试结果、评审结论和人工验收作为完成条件，增强结果可信度和责任可追溯性。

### 8.4 从代码孤岛到知识资产

通过代码逆向、需求恢复、测试约束和文档沉淀，将隐含在代码和人员经验中的系统知识转化为可理解、可验证、可维护的组织资产。

### 8.5 从项目方法到平台资产

将生产实践中验证有效的角色、技能、命令、审查规则和交付模板迁移到 AgentFlow，形成可复用、可演进的通用能力。

### 8.6 推广场景

- 存量系统需求恢复与重构改造；
- 新功能需求分析与开发；
- 缺陷定位和修复；
- 单元测试、集成测试补齐；
- 代码审查和变更影响分析；
- 研发交付报告与知识沉淀。

推广时应从低风险、边界清晰、结果容易验证的任务开始，根据实际效果逐步扩大范围。

## 第九章 后续计划

1. 在 AgentFlow 中选取代表性任务完成可审计的重放验证，补齐平台运行证据；
2. 固化需求逆向、TDD、集成测试、独立评审和交付报告模板；
3. 完善身份认证、权限控制、知识资产管理和审计能力；
4. 建立按任务类型划分的效率、质量、成本和人工介入评价基线；
5. 扩展更多研发场景，并持续优化 Agent 的通用性和评审标准。

## 结语

回扣全文核心：金融科技研发智能化的关键不是让模型无边界地替代人员，而是把模型能力纳入可编排、可验证、可追溯的人机协同流程。生产实践验证了代码逆向、TDD、独立审查和集成验证的可行性，AgentFlow 则将这些方法平台化，使其能够从单个案例推广为通用研发能力。

## 四、案例事实与证据确认清单

正式撰写正文前，需要由项目负责人逐项确认：

1. 案例系统可公开的匿名描述和实际改造范围；
2. 项目是整套重写、局部重构还是新增模块开发；
3. 实施周期“3 周”的准确起止时间和包含工作；
4. 人工投入的正确单位和统计方式；
5. 80% 覆盖率对应的模块、工具和测试报告；
6. 需求、单测和集成测试审查的真实记录；
7. 审查角色、开发技能和流程命令的准确数量；
8. 需求、设计、接口、测试、部署和运维文档的最终清单；
9. 可以脱敏展示的工作流、测试和交付证据；
10. 跨环境协作的审批、脱敏、数据使用和日志留存情况；
11. 已经迁移到 AgentFlow 的角色、流程和模板范围；
12. 是否已由 AgentFlow 对代表性任务完成重放或再次验证。

## 五、正式写作时的关键口径

### 推荐表达

- “生产实践验证了方法可行性，团队进一步将相关能力迁移并沉淀到 AgentFlow。”
- “平台辅助完成代码认知、材料整理、实现、测试和评审协同，人员负责关键业务决策与正式交付。”
- “案例系统名称和业务细节已做匿名化处理。”
- “实施效果以真实运行记录、测试报告和人工验收为依据。”

### 避免表达

- 在没有运行证据时声称原生产项目由 AgentFlow 从头完成；
- 将具体单点工具作为报告主体或创新点；
- 使用“完全无人值守”“自动修改生产系统”等高风险表述；
- 把目标系统的改造描述扩大为未经证实的整套重写；
- 使用未经核验的效率比例、成本金额、缺陷数量和资产数量；
- 隐去真实存在且与合规相关的跨环境数据处理问题。
